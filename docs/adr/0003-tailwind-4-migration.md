# Tailwind CSS v4 migration: CSS-first config, `@tailwindcss/vite`, Node 24 floor

We upgraded Tailwind CSS from 3.3.3 to 4.x as its own dedicated pass (per [ADR 0001](0001-selective-dependency-update.md)), scoped to a parity-preserving port of the existing setup rather than bundling in new v4 features or unrelated cleanup. Config moved fully to CSS: `tailwind.config.js` and `postcss.config.js` are deleted, `theme.extend` values live in a `@theme` block in `src/global.css`, and `autoprefixer`/`postcss` are removed since Tailwind v4 handles vendor-prefixing internally via Lightning CSS. We adopted the dedicated `@tailwindcss/vite` plugin (pinned `^4.3.3`, well past the `4.1.2` floor where a Qwik-specific missing-CSS bug was fixed) over the PostCSS plugin, since both Tailwind's and Qwik's own docs recommend it for Vite projects. `engines.node` and CI's `node-version` moved from `18.11.0` to `24` (current Active LTS) so the official `@tailwindcss/upgrade` codemod's Node 20+ requirement is met without pinning to an already-EOL runtime.

## Considered Options

- **`@config` compatibility shim** (keep `tailwind.config.js` as a v3-style JS file, referenced from CSS) — rejected: this is exactly the "CSS-based config" migration ADR 0001 called out as needing its own pass; using the shim would take on the version-bump risk while deferring that work again.
- **`@tailwindcss/postcss`** instead of the Vite plugin — rejected as the primary choice: official guidance favors the Vite plugin for Vite projects. Noted risk: the specific combination of Qwik + `qwikReact()` + `@tailwindcss/vite` is unverified by anyone outside this migration (the known Qwik bug was Qwik-general, not `qwikReact()`-specific); if that combination misbehaves, `@tailwindcss/postcss` is the fallback.
- **Node `>=20`** (the codemod's bare minimum) — rejected: Node 20 reached end-of-life in April 2026, before this migration happened. `>=22` (Maintenance LTS, ~8 months of support left at migration time) was also considered and rejected in favor of `>=24` (Active LTS, longest support runway).
- **Renaming the cryptic custom tokens** (`spacing.cust`, `spacing.padd`) while every token had to be touched anyway — rejected for this pass: kept as a separate, independently-reviewable cleanup rather than mixed into the version-bump diff.

## Consequences

- `vite.config.ts` and `adapters/vercel-edge/vite.config.ts` were renamed to `.mts`. `@tailwindcss/vite` ships ESM-only with no CJS export, and this project's config files were CJS-loaded (no `"type": "module"` in `package.json`) — the same class of problem ADR 0001 already flagged for `vite-tsconfig-paths`, but this time there's no older CJS-compatible release to pin to instead, since Tailwind v4 packages are ESM-only across the board. Forcing just the config files to load as ESM (via the `.mts` extension) resolves it without adopting `"type": "module"` project-wide, which would have a much larger blast radius. `build.server`'s script path and the adapter config's import of the root config were updated to match.
- `.cust-shadow` (previously `@layer components`) and `cursor-finger` (previously `theme.extend.cursor`) are now declared via the `@utility` directive — Tailwind v4 dropped automatic variant generation for `@layer`-defined classes, and `.cust-shadow` is used with `hover:cust-shadow` in `Navbar.tsx`; separately, v4 has no `--cursor-*` `@theme` namespace at all, so `cursor.finger` had no `@theme` path even before the variant question.
- Minimum supported browsers rose to Safari 16.4+, Chrome 111+, Firefox 128+ (Tailwind v4's floor, driven by native cascade layers/`@property`/`color-mix()`).
- CI now runs `pnpm build.client` in addition to lint/typecheck/test, closing the gap ADR 0001 flagged (no build step existed to catch a broken CSS/Vite pipeline).
- Follow-up work, if ever revisited: renaming `cust`/`padd` to something descriptive (touches `Navbar.tsx`, `ProjectList.tsx`, `Project.tsx`, `Info.tsx`, and 3 test files that assert on the literal class names); verifying the `qwikReact()` + `@tailwindcss/vite` combination holds up under real production traffic, not just local dev/build.
- Found post-migration, via manual browser QA: `grid-cols-[70%,30%]` (`Project.tsx`) and `grid-cols-[55%,45%]` (`Info.tsx`) silently broke. Tailwind v3's arbitrary-value parser normalized the comma to a space (`grid-template-columns: 70% 30%`); v4's rewritten engine passes it through literally as `grid-template-columns: 70%,30%`, which is invalid CSS and gets dropped, collapsing the grid to a single implicit column. Verified directly against a scratch `tailwindcss@3.4.19` build to confirm this was v3 behavior, not a pre-existing bug. Fixed by using Tailwind's documented underscore-for-space arbitrary-value syntax (`grid-cols-[70%_30%]`), which both versions handle identically. No other comma-separated arbitrary values were found elsewhere in the codebase.
